# Architecture

```
content/                     Markdown + YAML lessons, items, cases, labs, sources (authored)
scripts/                     content compiler and validator (Node), icon generator
tests/content/               tests for the compiler and validator (node --test)
ios/
  TrainerCore/               Swift package: all learning rules, no UI (swift test)
  SystemDesignTrainer/       SwiftUI app
    App/                     AppModel (state owner), ReminderService, app entry, onboarding
    UI/                      screens and components
    Resources/content/*.json compiled content (generated by `npm run content`; committed)
  SystemDesignTrainerUITests end-to-end tests that drive the app in the simulator
docs/                        decisions, curriculum, sources, testing, progress
```

## Data flow

1. Authors write `content/**`. `npm run content` validates everything (see
   `scripts/content-lib.mjs`) and writes `index.json` (metadata), `items.json`,
   `lessons.json`, `cases.json` and `labs.json`. Markdown becomes a small block model
   (paragraph, heading, list, table, code, quote, diagram), so the app renders natively
   without a web view. CI fails if the committed JSON is out of date.
2. At launch, `Catalog` (TrainerCore) decodes the bundle. `StateStore` loads the
   learner's state from `Application Support/SystemDesignTrainer/state.json`.
3. Views call `AppModel` methods. These call the pure `Engine` functions, then save. Only
   `Engine.record` writes attempts, and it updates the concept's schedule in the same step.
4. Everything the UI shows about progress is derived from the attempt log:
   `Mastery.status`, `Scheduler.dueConcepts`, `SessionComposer`, `AssessmentComposer`.

## TrainerCore modules

| File | Responsibility |
|---|---|
| `Content.swift` | Codable content models and `Catalog` lookups |
| `State.swift` | Persisted state: attempts, per-concept review records, results, preferences. Lenient decoding fills defaults for fields added later. |
| `Time.swift` | `LocalDay` (calendar-day arithmetic immune to DST) and an injectable `Clock` |
| `Scheduler.swift` | Per-concept interval ladder and update rules |
| `Mastery.swift` | Concept states, needs-review reasons, summaries, calibration, weak topics |
| `Checker.swift` | Answer checking: choices, numeric tolerance and parsing, ordering, rubric self-assessment |
| `Selection.swift` | Item choice that avoids repeats; reviews become delayed checks at long intervals |
| `Session.swift` | Daily session composition and recap |
| `Assessment.swift` | Topic quiz, delayed check, cumulative, final; separate auto and self scores |
| `Engine.swift` | The state mutations the app performs |
| `Persistence.swift` | `StateStore` (atomic writes and a backup copy), `Migrations`, `Backup` export/import, `ReminderPlan` |

## Practice versus assessment

Items carry a `pool`. **Practice** items appear after lessons and in spaced reviews, with
hints and immediate feedback. **Assess** items appear only in quizzes and delayed
retention checks, without hints, and feedback comes only after submission. **Final** items
appear only in the final assessment. Because the pools are separate, an assessment never
reuses a question whose solution was just shown. A concept counts as *Retained* only when
a different item is answered correctly without help at least 7 days after the previous
retrieval.

## Reminders

`ReminderService` keeps exactly one pending request, with identifier
`daily-study-reminder`. It is a repeating calendar trigger on hour and minute (15:00 by
default). Each change of preferences, and each time the app becomes active or goes to the
background, removes the pending request and adds a new one, so duplicates cannot build up
and the body text stays current ("3 concepts due for review · next lesson: …").
Calendar triggers follow the phone's current time zone.

## Persistence and migration rules

- Every write is atomic (`Data.write(.atomic)`). The previous file is copied to
  `state.bak.json` first, but only if it is readable.
- On load: try the main file, then the backup. If neither can be read, move both aside
  (they are never deleted) and start fresh, and tell the user.
- `AppState.currentSchemaVersion` is the stored version. A field that only adds data
  needs no migration. Renames or restructures add a step to `Migrations.steps` and bump
  the version. Attempts are never dropped. Data from a newer app version is rejected,
  not mangled.
- Content ids are permanent. Removed content leaves its attempts in place, and the app
  ignores unknown ids.

## Extending

- **New lesson:** add a file following `docs/CONTENT_GUIDE.md`, run `npm run content`,
  commit the regenerated JSON, and build.
- **New question type:** add a format to the validator, `ItemFormat`, `Checker`,
  `AnswerDraft` and `AnswerInput`.
- **Changing a learning rule:** edit TrainerCore, update the tests, and update
  `docs/LEARNING_DESIGN.md`.
